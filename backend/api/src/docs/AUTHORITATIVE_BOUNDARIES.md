# Authoritative System Boundaries

Defines which ThryftVerse systems are authoritative (non-ML) and where ML
may participate as decision support only. This is enforced in code, not
just policy — each section cites the file and guard that implements it.

Aligned with NIST AI RMF 1.0 (Govern, Map, Manage) and the ML flagship
analysis report §8.1 risk tiers.

---

## Risk Tiers

| Tier | Automation ceiling | ThryftVerse examples |
|------|-------------------|----------------------|
| **Low** | Automated with rollback and controls | feed ranking, similar-items, image crop suggestion |
| **Medium** | Human confirmation / review for material outcomes | catalogue attribute mapping, duplicate suggestion, moderation triage, price range advice |
| **High** | Model may provide evidence/priority only; authoritative policy and accountable review own action | fraud restriction, reserve/escrow, auction integrity, KYC/AML, payout, account enforcement |

---

## High-Tier — Non-ML Authoritative Systems

These systems are **never** governed by ML output. ML may surface evidence
or priority for human review, but the authoritative decision and action
belong to deterministic code, policy rules, and accountable human review.

### Payments

- **Authority:** `routes/payments.ts`, `routes/webhooks.ts`,
  `lib/paymentProviders.ts`, `lib/stripePaymentMethods.ts`
- **Boundary:** Payment intent creation, capture, refund, and dispute
  handling are delegated to licensed payment providers (Stripe, etc.)
  via deterministic API calls. No ML model decides whether a payment
  succeeds, fails, or is held.
- **Enforcement:** Provider webhook signatures are verified; settlement
  state transitions are idempotent and guarded by
  `paymentTablesAvailable()` checks.

### Payouts

- **Authority:** `routes/payouts.ts`
- **Boundary:** Payout scheduling and settlement require security-admin
  access (`ensureSecurityAdminAccess`). Payout status transitions are
  idempotent via `settlePayoutRequest`.
- **Enforcement:** Mock payout webhooks are disabled in production
  (`config.nodeEnv !== 'production'` guard). No ML path exists to
  initiate or approve a payout.

### KYC / AML

- **Authority:** `lib/kycProviders.ts`, `routes/compliance.ts`,
  `lib/compliance.ts`
- **Boundary:** Identity verification status is determined by the KYC
  provider (Stripe Identity, Persona, Onfido), not by an ML model.
  AML alerts are generated by deterministic transaction-monitoring
  rules and routed for human review.
- **Enforcement:** KYC status (`pending`, `in_review`, `approved`,
  `declined`, `expired`) is set exclusively from provider webhook
  callbacks. No code path allows ML to set KYC status.

### Auction Ordering and Integrity

- **Authority:** `routes/auctions.ts`,
  `workers/handlers/auctionSweepHandler.ts`
- **Boundary:** Auction winner determination is deterministic:
  `ORDER BY amount_gbp DESC, created_at ASC, id ASC`. The highest bid
  wins; ties are broken by earliest bid timestamp, then by sequential
  row id. No ML model reorders, scores, or overrides auction results.
- **Enforcement:** Auction settlement is a single database transaction
  with `FOR UPDATE SKIP LOCKED` on the auction row. Ledger entries are
  posted deterministically from the winning bid amount and a fixed
  platform fee rate.

### Settlement and Escrow

- **Authority:** `lib/reconciliation.ts`,
  `workers/handlers/reconciliationHandler.ts`,
  `workers/handlers/auctionSweepHandler.ts`
- **Boundary:** Settlement postings are deterministic ledger entries
  derived from transaction amounts and fixed fee rates. Escrow holds
  are governed by buyer-protection time windows, not ML predictions.
- **Enforcement:** Reconciliation compares committed state against
  idempotency keys and request hashes. Unknown outcomes
  (`outcome_unknown`) are never collapsed to `success` or `failed`.

### Account Restriction

- **Authority:** Admin action via `routes/admin.ts`,
  `routes/fraudDetection.ts`
- **Boundary:** Account suspension, ban, or restriction is a human
  admin decision. The fraud detection system computes risk scores and
  surfaces evidence, but does not autonomously restrict accounts.
- **Enforcement:** `lib/fraudDetection.ts:checkFraudNonBlocking()`
  is advisory by design — it logs and scores but never throws or
  blocks the user flow. The `block` action is computed for audit
  and priority routing, but no code path allows the fraud system to
  directly mutate account status. Fraud reports
  (`POST /fraud/report`) are stored for moderator review.

### Reserve / Escrow (1ze Token Pricing)

- **Authority:** `lib/pricingEngine.ts`
- **Boundary:** The 1ze token pricing engine is deterministic,
  bounded-parameter commerce logic. Buy/sell/cross-border prices are
  calculated from fixed markup/markdown bps, PPP factors, and
  operator-set FX rates. No ML model sets token prices.
- **Enforcement:** `validatePricingProfileInput()` enforces hard
  bounds on all parameters (markup 1500–2500 bps, markdown 1000–2000
  bps, cross-border fee 500–1500 bps, PPP 0.7–1.0).
  `findPricingArbitrageViolations()` deterministically detects
  arbitrage opportunities. All rates are operator-set via
  `setOnezeAnchorConfig()` and `setInternalFxRate()`.

## Medium-Tier — Human Confirmation Required

ML may produce suggestions or triage, but material outcomes require
human confirmation before they take effect.

### Catalogue Attribute Mapping (Importer)

- **ML role:** Source field → canonical category/condition/size mapping
  with confidence scores.
- **Human gate:** `workers/handlers/catalogImportNormalisationHandler.ts`
  sets low-confidence or missing fields as `blocking_issues` and
  transitions the item to `needs_input`. The batch transitions to
  `awaiting_seller` (or `awaiting_operator` for operator-level
  blockers). No item with blocking issues can be approved.
- **Enforcement:** `domain/catalogImports/catalogImportService.ts:approveBatch()`
  rejects any item whose `readiness !== 'ready'` or whose
  `blocking_issues` array is non-empty. The state machine guard
  requires batch status `awaiting_seller` before approval.

### Duplicate Resolution (Importer)

- **ML role:** `mapping/catalog/index.ts:detectDuplicates()` computes
  similarity scores across title, brand, size, and media hash.
- **Human gate:** Items above the duplicate threshold are set to
  `readiness = 'probable_duplicate'` with a `probable_duplicate`
  blocking issue. The seller must review and either exclude or
  confirm the item.
- **Enforcement:** Same `approveBatch()` guard — `probable_duplicate`
  items cannot pass the `readiness === 'ready'` check.

### Pricing Advice (Importer Currency)

- **ML role:** None — currency resolution is deterministic. The
  boundary is documented here because future ML price-range
  suggestions would fall into this tier.
- **Human gate:** `mapping/catalog/currencyPolicy.ts:resolveCurrency()`
  never auto-converts non-GBP currencies. Non-GBP source prices are
  set to `priceGbp = 0` with `low` confidence and reason code
  `non_gbp_requires_confirmation`. The seller must confirm the GBP
  price in the review workbench.
- **Enforcement:** Low-confidence price fields become blocking issues
  in the normalisation handler, preventing approval without seller
  confirmation.

### Moderation Triage

- **ML role:** `lib/moderation/` providers (Rekognition, Sightengine)
  classify images and text as `approved`, `rejected`, or `review`.
- **Human gate:** `review` status maps to `moderation_pending` — the
  asset stays in that state until a human admin approves or rejects
  it via `POST /moderation/review/:assetId`.
- **Enforcement:** `routes/moderation.ts` — the manual review endpoint
  requires `admin` role and only operates on assets in
  `moderation_pending` or `review` status. No code path allows ML to
  force an asset to `publishable` without either provider approval
  or human review.

## Generated Content — No Unreviewed Publication

### Bot / Agent Responses

- **Authority:** `botRuntime/openaiAgent.ts`, `botRuntime/index.ts`
- **Boundary:** AI-generated agent responses below the confidence
  threshold (default 0.6) are not published as the agent's reply.
  The response is replaced with a human-fallback message and the
  draft is stored in metadata for moderator review.
- **Enforcement:** `openaiAgent.ts:buildSuccessResult()` — when
  `confidence < threshold`, `needsHumanReview = true` and
  `buildHumanFallbackText()` replaces the published text with:
  "I'm not confident enough in my response to post it directly.
  A human moderator should review this before it is shared."
  The original draft is preserved in `metadata.draftResponse`.

### Catalogue Import Publication

- **Authority:** `domain/catalogImports/catalogImportPublication.ts`
- **Boundary:** Imported items are published as **draft** listings
  (`status = 'draft'`), never as `active` or `live`. The seller must
  separately activate each draft listing after reviewing it.
- **Enforcement:** `publishBatch()` → `createDraftListing()` inserts
  with `status = 'draft'`. The publication receipt reports
  `liveCount: 0` and `draftCount` — activation is a separate,
  seller-initiated action outside the import pipeline.

### Catalogue Import Attestation

- **Authority:** `domain/catalogImports/catalogImportService.ts:approveBatch()`
- **Boundary:** Batch approval requires a signed attestation from the
  seller confirming: (1) they own the rights to the listings,
  (2) the facts are accurate, and (3) no buyer data is included.
- **Enforcement:** `validateAttestation()` rejects approval if any
  of `ownsRights`, `accurateFacts`, or `noBuyerData` is false. The
  attestation is recorded in the batch event log with `approvedBy`
  and timestamp.

## Low-Tier — Automated with Controls

### Feed Ranking, Similar Items, Crop Suggestion

- **Authority:** ML models with rollback and monitoring controls.
- **Boundary:** These systems may operate autonomously because their
  outcomes are reversible (feed re-ranking), non-material (similar
  item suggestions), or advisory (crop suggestions the user can
  ignore). No financial, identity, or enforcement outcome is
  produced.

---

## Verification Checklist

To confirm a boundary is real, not decorative:

1. **Trace the code path** from ML output to material action. If no
   path exists, the boundary holds.
2. **Check the state machine guard.** Medium-tier actions must pass
   through a human-gated state (`awaiting_seller`, `moderation_pending`).
3. **Check the role guard.** High-tier admin actions must require
   `admin` or security-admin role.
4. **Check the idempotency guard.** Money movement must be idempotent
   and reconcilable.
5. **Check the determinism of ordering.** Auction and settlement
   ordering must be a total order with no ML input.
